# Troodon: Метрики (Prometheus)

Цей документ описує, як працює збір метрик у Troodon Edge Proxy, як їх вмикати, та що саме ми віддаємо для моніторингу типу Grafana.

---

## 1. Як увімкнути метрики

Метрики Prometheus за замовчуванням вимкнені. Щоб їх увімкнути, необхідно додати параметр `prometheus_port` у глобальний блок `server` конфіг-файлу `config.yaml`:

```yaml
server:
  listen_addr: "0.0.0.0"
  listen_port: 80
  prometheus_port: 9090  # <--- Вмикає експорт метрик на порт 9090
  prometheus_listen_addr: "127.0.0.1" # Опціонально: біндинг (дефолт 127.0.0.1)
  log_level: "info"
```

Коли проксі стартує з цим параметром, сервер підіймає додатковий TCP-слухач спеціально для Prometheus метрик. **Важливо:** за замовчуванням він "слухає" лише на `127.0.0.1` для забезпечення безпеки (metrics isolation). Якщо вам потрібно відкрити їх назовні, змініть `prometheus_listen_addr` на `0.0.0.0`.

В Prometheus конфігурації (scrape config) додайте цей порт для збору:
```yaml
scrape_configs:
  - job_name: 'troodon_edge'
    static_configs:
      - targets: ['127.0.0.1:9090']
```

## 2. Які метрики ми збираємо?

Ми контролюємо кожне з'єднання через наш власний proxy framework (надбудова над Pingora) та спеціально експортуємо лише дві найважливіші кастомні метрики нашого L7 шару. Це гарантує мінімальний оверхед.

### 2.1 `troodon_http_requests_total`
**Тип:** Лічильник (`Counter`)
**Опис:** Загальна кількість HTTP-запитів, які пройшли через проксі від моменту його запуску. Дозволяє вираховувати загальний **RPS (Requests Per Second)**.

### 2.2 `troodon_http_request_duration_seconds`
**Тип:** Гістограма (`Histogram`)
**Опис:** Тривалість HTTP-запитів (латентність) від моменту їх початку до моменту завершення або помилки. Дозволяє будувати **Перцентилі (p50, p90, p99)** швидкості відповіді бекендів. Набагато корисніше ніж просто середній час (average).

## 3. Лейбли (Labels)

Обидві метрики мають однаковий набір лейблів, що дозволяє фільтрувати графіки в Grafana:

| Лейбл | Деталі / Приклади | Опис |
|---|---|---|
| `method` | `GET`, `POST`, `OPTIONS` | HTTP метод запиту. |
| `status` | `1xx`, `2xx`, `3xx`, `4xx`, `5xx`, `unknown` | Клас HTTP статус-коду відповіді. |
| `host` | `api.example.com`, `unknown` | SNI або Host заголовок запиту (`effective_host`). |

> **Чому статуси згруповано (напр. `2xx` замість `200`)?**
> Щоб уникнути проблеми "cardinality explosion" у базі даних Prometheus. Якщо застосунок динамічно віддає сотні різних (або нестандартних) статус-кодів, це може призвести до надмірного навантаження на пам'ять Prometheus. Замість цього ми групуємо їх у 5 основних класів. Якщо потрібен детальний розбір (напр. різниця між 401 та 404), краще аналізувати access лог (де є повний статус).

## 4. Чи віддаємо ми метрики CPU та Memory (RAM)?

**Ні, поточна версія Troodon не експортує метрики CPU та RAM внутрішньо через порт Prometheus.**

### Чому?
Зазвичай в екосистемі Rust бібліотека `prometheus` має feature `process` (процес-колектор), який автоматично експортує `process_resident_memory_bytes` та `process_cpu_seconds_total`. 

Проте під час розробки ми зіштовхнулися з вразливістю у залежностях (crate `protobuf` < 3.7.2). Щоб гарантувати **максимальну безпеку** нашого Edge Proxy і позбутися всіх старих та вразливих C++ / Rust залежностей, ми жорстко вимкнули дефолтні фічі в `Cargo.toml`:
```toml
prometheus = { version = "0.13", default-features = false }
```
Це відключило збір стандартних метрик процесу з боку самого додатку.

### Як моніторити CPU / RAM для Troodon?
Edge Proxy, як правило, розгортається в контейнерах (Docker / Kubernetes) або як Linux Systemd сервіс. У Production середовищі моніторинг ресурсів OS є зоною відповідальності системного рівня:

1. **Kubernetes:** Використовуйте стандартні метрики `cAdvisor` (напр., `container_memory_working_set_bytes` або `container_cpu_usage_seconds_total`), фільтруючи по pod / container імені.
2. **Docker:** Використовуйте `cAdvisor` або `docker stats`.
3. **Linux / Systemd:** Використовуйте `node_exporter` від Prometheus, який збирає детальну інформацію про кожен процес без вбудовування логіки в сам балансувальник бази (як це робить Nginx/Envoy). 

Це відповідає найкращим практикам (SoC - Separation of Concerns). Проксі експортує виключно бізнес і L7 метрики (RPS, Latency), а інфраструктура відповідає за CPU/RAM.
